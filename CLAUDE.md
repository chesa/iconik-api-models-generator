# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working
with code in this repository.

## What this project does

A CLI tool (`generate-iconik-models`) that downloads the OpenAPI v3
specs for the iconik MAM/DAM API and generates a Pydantic v2 models
package from their `components.schemas`. The entire generator is one
script: `src/generate_iconik_models.py`. There is no `models/` package
checked into the repo — it's build output, regenerated by running the
tool. `examples/models/` holds a sample of that generated output for
reference.

## Commands

Install (editable, with dev tools):

``` bash
pip install -e ".[dev]"        # dev tools: pylint, ruff, yapf, isort, pycln, mypy, pytest
pip install -e ".[formatters]" # just pycln, isort, yapf
```

Run the generator:

``` bash
generate-iconik-models                      # writes to ./models
generate-iconik-models -o OUTPUT_DIR -F      # custom dir + auto-format output
generate-iconik-models --keep-downloads      # keep _specs/*.json alongside generated modules
generate-iconik-models --debug
```

Lint/format the generator source itself (mirrors
`bitbucket-pipelines.yml`'s `lint` step — run against `src/`, not
`models/`):

``` bash
ruff --config pyproject.toml check src/
pylint --rcfile pyproject.toml --recursive yes src/
yapf --diff --recursive src/
```

Test:

``` bash
pytest -v tests/*
pytest -v tests/test_dummy_module.py::test_add   # single test
```

Format code that the tool *generates* (only relevant when working on
the code-formatting step of the generator, or manually cleaning
generated output — see `format_generated_code()`):

``` bash
pycln --all models/
isort models/
yapf -i models/*.py
```

## Architecture

`src/generate_iconik_models.py` is a single linear pipeline, driven by
`main()`:

1.  **`download_specs`** — fetches each name in `SPEC_NAMES` from
    `BASE_URL.format(spec_name)` (`https://app.iconik.io/docs/{}/spec/`)
    and saves raw JSON to `<output_dir>/_specs/`.
2.  **`extract_all_schemas`** / **`extract_schemas`** — pull
    `components.schemas` out of each downloaded spec. `extract_all_schemas`
    flattens every spec's schemas into one dict (used for cross-spec `$ref`
    resolution); `extract_schemas` keeps them grouped per spec (used to
    decide which module each model belongs to).
3.  **`generate_models`** — for each spec, converts each schema into a
    model dict (either a Pydantic `class` definition or a type-alias
    for `oneOf`/`anyOf` unions), then **`sort_models_by_dependency`**
    topologically orders them so a model is always defined after
    anything it references without a `$ref` (forward refs across specs
    are still handled via string literals, see below).
      - **`generate_model_field`** turns one OpenAPI property into a
        Pydantic field (type hint + `Field(...)` default/constraints).
      - **`openapi_type_to_python`** maps primitive OpenAPI
        type/format pairs (e.g. `string`+`date-time`) to Python types.
      - **`handle_oneof_anyof`** builds `Union[...]` type hints,
        quoting model names not yet defined in the same module as string
        forward references.
4.  **`create_module_file`** — writes one `.py` file per spec (e.g.
    `assets.py`), scanning generated field types to decide which
    imports (`datetime`, `UUID`, `HttpUrl`, `Literal`, etc.) are needed,
    then appends `Model.model_rebuild()` calls for every model to
    resolve forward references at import time.
5.  **`create_package_files`** — writes the package `__init__.py`:
    imports every generated module, stamps a calendar version
    (`get_calendar_version`, format `YYYY.M[.P][-modifier.N]`), and
    embeds an `__info__` dict with each spec's OpenAPI version/title.
6.  **`format_generated_code`** — if `-F/--format-code` was passed, runs
    `pycln` → `isort` → a `sed` pass that strips trailing whitespace
    *and* deletes every blank line → `yapf` over the *generated*
    package (not over the generator's own source).

Spec name → module name: hyphens become underscores (e.g.
`users-notifications` spec → `users_notifications.py` module), driven
by `SPEC_NAMES` at the top of the file.

## Known repo inconsistencies (don't "fix" without asking)

  - `src/dummy_module/` and `tests/test_dummy_module.py` are placeholder
    scaffolding kept only to give the CI pipeline something importable
    to lint/test/version-check — they are unrelated to the actual model
    generator and contain a toy `Calculator` class.
  - `bitbucket-pipelines.yml`'s `test` step measures coverage against
    `src/dummy_module`, and the `build-push-pypi`/tag-verification step
    imports `dummy_module.__version__` — neither currently touches
    `generate_iconik_models`, so CI does not actually test or version-gate
    the real generator logic.
  - `pyproject.toml` still declares the dynamic version as
    `generate_iconik_models.__version__` and the console script as
    `generate-iconik-models = "generate_iconik_models:main"`, which is
    the source of truth for the actual package — the pipeline's
    `dummy_module` references above are the odd ones out.
